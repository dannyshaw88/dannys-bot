What happened and what was fixed
The actual bug in the throttle formula
Before the fix, apiThrottle() rolled calls and secs as two independent random values:

calls = random(requestsMin … requestsMax)
secs  = random(everySecondsMin … everySecondsMax)
delay = secs / calls

This lets the worst extremes combine. Example — if your API Controls say "1–5 requests per 60–120 seconds":

Roll	calls	secs	delay
Lucky (intended worst case)	5	120s	24 seconds
Unlucky (bug)	5	60s	12 seconds
The unlucky roll combines the largest calls with the smallest secs — a combination that's outside either endpoint of your configured range. That's the bug.

After the fix, the formula computes the valid delay range directly:

fastest = everySecondsMin / requestsMax   ← legitimate minimum
slowest = everySecondsMax / requestsMin   ← legitimate maximum
delay   = random(fastest … slowest)

Every call now lands inside your intended range, no exceptions.

The other contributing factors (no code change needed, but be aware)
Pagination hits the throttle on every page — if you set View Timeline Feed to 20+ posts and Instagram returns 15 per page, page 2 is a full throttled API call. With a 60-second throttle that's 2 minutes just loading the feed.

Media/seen calls are chunked into batches of 4, each is throttled — viewing 16 posts = 4 throttled API calls, not 1.

likeTimelinePosts fetches the timeline again even when called right after viewTimelineFeed — the feed data is not reused between them. This is a future optimisation, not the cause of the ban.

Recommendation for @fili_z8141's replacement account: keep viewTimelineFeedMax at 10 or below and set your API Controls to something like 1 request min / 3 requests max per 60s–120s so the worst-case delay stays above 20 seconds per call.
